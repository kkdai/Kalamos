# ADR 0001：以 TypeScript 建置純前端編輯器

**狀態：未採用。** 自管資料庫需求已取代此純前端提案，見 [ADR 0002](./0002-self-managed-database.md)。以下保留原提案。

## 背景

原始 Web 版提案建議首版只需開啟、編輯、救回與下載單一 Markdown 文件，不需帳號、同步或後端處理。現有專案已使用 [TypeScript、Vite 與 CodeMirror 6](../../../package.json)，但[編輯器部分功能](../../../src/editor/index.ts)仍會透過[圖片](../../../src/editor/images.ts)和[連結](../../../src/editor/live-preview.ts)模組接觸 Tauri；[瀏覽器測試](../../../tests/e2e/helpers.ts)走的是[記憶體模擬](../../../src/ipc.ts)，並非可交付的檔案儲存方案。現行 [GitHub Pages 工作流程](../../../.github/workflows/pages.yml)也只部署 `site/`，不會發布編輯器。

## 決策考量

- 重用既有 Markdown 編輯行為，不另寫一套即時預覽。
- 讓文件留在瀏覽器內，開檔和下載不依賴 Tauri、Rust 或應用程式伺服器。
- 避免為單文件流程引入前端框架或改動桌面版與官網的部署。

## 考慮過的方案

1. **TypeScript + Vite，直接使用瀏覽器 API。** 沿用現有工具與編輯器；需要把實際用到的桌面檔案、圖片及連結行為與瀏覽器入口分開。
2. **使用 React 等 UI 框架，仍以 CodeMirror 為編輯器。** 若之後要維護多個複雜畫面，有共同的狀態與元件模式；首版只有單一編輯畫面，先採用會增加整合成本，仍須處理相同的瀏覽器儲存限制。
3. **以後端儲存或處理文件。** 便於日後做跨裝置同步或伺服器轉檔，但會引入資料傳輸、維運與隱私負擔。首版沒有這類需求。

## 建議決策

採方案 1。Web 入口與檔案流程放在 `web/`；應用程式程式碼用 TypeScript，畫面用 HTML 與 CSS，Vite 產出可靜態託管的資源。不新增 UI 框架或應用程式後端。共用 CodeMirror 與現有可跨平台的 Markdown 編輯邏輯；遇到桌面相依的行為，透過明確的介面改接瀏覽器實作，不把桌面入口或測試模擬當成 Web 產品入口，也不預先重寫整個桌面應用程式。

本機文件透過瀏覽器選檔與下載，首版不依賴能寫回原檔的 File System Access API。草稿建議用 IndexedDB（瀏覽器內建的本機資料庫），與使用者下載保存的檔案分開。儲存是否成功以瀏覽器實際回報為準，不等同於永久備份。

## 影響與驗證

- 可使用靜態託管，也不需為文件內容維護應用程式伺服器。發布位置與官網入口另行確認，不修改現有的 `site/` 部署。
- 共用編輯行為時，應確認桌面版原有測試仍通過；Web 版須另用不含 Tauri 及測試模擬的正式產物，在實際瀏覽器驗收開檔、下載、重新開啟後的草稿救回，以及載入後的斷網流程。
- 若將來要直接覆寫本機檔，需要重新評估瀏覽器權限與相容性；若要同步、協作或伺服器轉檔，再以新 ADR 評估後端。兩者都不是首版採用框架或後端的理由。
